# MVP 정의서

> 처음 만든 날: 2026-10-20. MVP(최소 기능 제품)는 "처음 사용자 손에 쥐여 줄 때 이것만은 있어야 하는 것"입니다.
> 이 폴더는 그 MVP를 **두 가지로 나눠** 정의하고, 에이전트가 MVP를 정하고 만들 때 따를 가이드를 담습니다.

## 1. 두 가지 MVP

| | 공통 MVP (`common/`) | 고유 MVP (`silvercare/`) |
| --- | --- | --- |
| 뜻 | **어느 프로젝트에나** 있어야 하는 기본기 | **이 프로젝트만의** 존재 이유 |
| 예 | 로그인, 내 정보, 설정, 권한 안내, 오류·연결 끊김 화면, 화면 규칙 | 말동무 대화, 위급 필터, 픽업 대기와 브리핑 |
| 누가 정하나 | 한 번 정해 두고 프로젝트마다 가져다 씀 | 프로젝트 주인이 방향 문서(`../DIRECTION.md`)를 보고 정함 |
| 바뀌는 때 | 드묾. 여러 프로젝트에 걸친 배움이 있을 때 | 회차마다 |
| 프로젝트 이름 | 쓰지 않음. 다른 저장소에 그대로 복사해도 맞아야 함 | 씀 |

**가르는 질문 하나**: "이 기능을 지우면 이 프로젝트가 다른 앱과 구별되지 않게 되나?" 그렇다면 고유, 아니면 공통입니다.
로그인을 지워도 실버케어는 실버케어이지만, 말동무를 지우면 실버케어가 아닙니다.

## 2. 폴더

```
docs/mvp/
  README.md                 이 가이드
  common/                   공통 MVP. 프로젝트 이름이 나오지 않음
    requirements.md         공통 기능 요구사항 (MVP-C-…) 과 화면 규칙 (MVP-UI-…)
    screens.md              공통 기본 화면 목록과 화면마다 꼭 있어야 할 것
    templates/screen.md     화면 하나의 세부 명세 틀
  silvercare/               이 프로젝트의 MVP
    mvp.md                  고유 MVP 범위, 공통 MVP를 어떻게 들여왔나, 끝났다고 볼 기준
```

새 프로젝트를 시작하면 `common/`은 그대로 복사하고, `silvercare/` 자리에 그 프로젝트 이름의 폴더를 새로 만듭니다.

## 3. 명세 체계와의 관계

```
 docs/DIRECTION.md          왜 만드나
 docs/mvp/<프로젝트>/mvp.md  처음 내놓을 범위 (고유 + 들여온 공통)   ← 이 폴더
 docs/mvp/common/           공통 기본기
 docs/specs/                그 범위를 만들 수 있게 쪼갠 명세 (요구사항 → 중위 → 하위)
```

- `docs/specs/requirements.md`의 사용자·개발자 요구사항은 **고유 MVP**를 풀어 쓴 것입니다.
- 공통 MVP는 `docs/specs/`에 다시 적지 않습니다. 하위 명세가 공통 기능을 쓸 때는 `MVP-C-03`처럼 번호로 가리킵니다.
- 프로젝트가 공통 MVP를 바꿔 써야 하면(예: 어르신 화면에는 로그인이 없음) 공통 문서를 고치지 않고 `mvp.md`의 "들여오기" 표에 **바꾼 점과 이유**를 적습니다.

## 4. 에이전트 가이드

### 4.1 MVP를 정할 때

1. 기능 후보를 모두 적고, 1절의 질문으로 공통과 고유로 가릅니다.
2. 고유 MVP는 북극성(`DIRECTION.md` 2절)에 닿는 데 꼭 필요한 것만 남깁니다. 나머지는 `mvp.md`의 "MVP 밖" 표로 옮기고 이유를 적습니다.
3. 공통 MVP는 `common/requirements.md`에서 이 프로젝트에 필요한 것을 고르고, 들여오기 표에 "그대로 / 바꿔서 / 안 씀"으로 적습니다. "안 씀"과 "바꿔서"에는 이유를 답니다.
4. 정한 것은 초안 PR로 올리고 주인 확인을 받습니다. MVP 범위는 목적에 닿는 결정이라 주인이 정합니다 (`DIRECTION.md` 5절).

### 4.2 화면을 명세할 때 (공통 MVP와 고유 MVP 모두)

1. **화면 목록 먼저**: 화면은 목록(`common/screens.md`, 프로젝트의 `../screens.md`)에 먼저 오르고, 그다음 피그마에 그려지고, 그다음 화면 명세가 쓰입니다. 목록에 없는 화면은 만들지 않습니다.
2. **기능 화면만 보지 않기**: 기능 화면을 정하면 반드시 `common/screens.md`를 훑어 빠진 기본 화면(로그인, 내 정보, 설정, 권한, 오류 등)이 없는지 확인합니다.
3. **한 화면에 명세 한 편**: [templates/screen.md](./common/templates/screen.md) 틀을 씁니다. 절을 지우지 않고, 쓸 것이 없으면 "해당 없음".
4. **다섯 가지 모습**: 모든 화면은 기본, 불러오는 중, 비어 있음, 오류, 연결 끊김을 명세하고 피그마에도 다섯 프레임을 그립니다 (MVP-UI-01).
5. **값은 이름으로**: 색, 글씨 크기, 간격, 둥글기는 피그마 변수 이름으로만 씁니다. 숫자를 코드에 바로 쓰지 않습니다 (MVP-UI-02).
6. **컴포넌트는 짝으로**: 반복되는 요소는 피그마 컴포넌트 하나와 코드 부품 하나가 짝입니다 (MVP-UI-03).
7. **문구는 표로**: 화면에 보이는 글은 모두 명세의 문구 표에 있습니다 (MVP-UI-04).
8. **이동은 지도로**: 앱마다 화면 지도(어느 화면에서 무엇을 하면 어디로) 한 장을 둡니다 (MVP-UI-07).

### 4.3 MVP가 끝났다고 볼 때

`mvp.md`의 "끝났다고 볼 기준"이 모두 맞고, 들여온 공통 MVP 항목의 수락 기준이 모두 통과하고, 주인이 실제 기기에서 한 번 돌려 봤을 때입니다.
